🧠 Human-Eye Perception Contrast Engine (Text Color Swapping)

The mechanism that automatically switches the text color inside the cells between "White (#FFFFFF)" and "Black (#000000)" is controlled by a mathematical logic: "It calculates the brightness (luminance) of the background color in real-time using JavaScript, and if it exceeds a certain threshold, the text becomes black; otherwise, it becomes white."

1. Actual Control Code

Inside the cell renderer of this page, the black/white determination for the text color is made by the following simple function: 

function getTextColorForBg(brightness) {
  // Function to determine whether text color should be black or white based on background brightness
  return brightness > 140 ? "#000000" : "#FFFFFF";
}

2. Switching Mathematical Algorithm and the Reason for "140"

When generating each row, the variable i (coordinate value from 0 to 255) directly represents the "luminance (brightness)" of each color.

  • For Bright Background Colors (i > 140): For example, when i = 200 (bright yellow, cyan, white, etc.), the background is bright enough that if white text is placed on it, it will blend in and become unreadable. The function returns #000000 (black text).
  • For Dark Background Colors (i ≤ 140): For example, when i = 80 (dark red, blue, dark gray, etc.), the background is dark, so black text would be crushed. The function returns #FFFFFF (white text).

❓ What is the threshold value "140"?

Within the brightness scale from 0 to 255 (256 steps), this is a value designed and calculated under the premise that "inverting the text color at this boundary yields the highest text visibility." The mathematical and design reasons are based on the following two points.

  1. "Correction" from the Median of Brightness (0-255): The exact middle value (median) between 0 and 255 is mathematically 127 (or 128). However, the human eye is very sensitive to changes in "dark colors (black)" and inversely, somewhat insensitive to "bright colors (white)". If the boundary value were set exactly in the middle at 128, then at i = 130, which is an "intermediate color still somewhat dark and close to gray", it would be judged as "bright" and switch to black text. At this point, the darkness of the background and the black text would blend, making it very hard to read. Therefore, by setting the boundary value slightly higher than the middle (shifted towards the bright side) to 140, it secures a visual safety margin where "subtle intermediate areas leaning towards gray are safely displayed in white text, and only areas where the background is definitively bright become black text."
  2. Design Based on WCAG (Web Accessibility Guidelines): The international standard defining web contrast ratios (WCAG) also recommends securing a slightly wider application range for white text (increasing the contrast ratio) as the most visually legible design pattern. This "brightness 140" is based on the "golden ratio of black-and-white inversion" in those guidelines.

3. Visual "Sensitivity Ratio of Primary Colors of Light (Correction)" for Each Channel

Furthermore, humans have a visual characteristic (luminous efficiency) where "Green (G) is perceived as very bright, and Blue (B) as very dark." Therefore, instead of evaluating uniformly just by the value of i, we multiply a "blend ratio of brightness perceived by humans" for each cell's background color before passing it to the threshold. 

// Red Cell (R) : Appears brighter than blue, so judged with a 30% attenuation correction
color: getTextColorForBg(i * 0.3)

// Yellow Cell (R+G) : Very bright mix of red and green, judged with a 90% correction (likely black text)
color: getTextColorForBg(i * 0.9)

// Blue Cell (B) : Appears the darkest and most sunken, judged with a 10% correction (almost always white text)
color: getTextColorForBg(i * 0.1)

By this correction, it perfectly synchronizes with the physical luminous intensity of the color code itself (the brightness seen by the human eye), instantaneously switching black and white text to be maximally legible.

🔄 Logic Pipeline (Data Processing & Rendering Order)

The processing sequence from when this table outputs color codes upon user interaction (button switching) or loading until filtering occurs is based on the following logical flow:

  1. 1. Detect User Selection (Determine Global State):
    Reads the state values of "Render Mode (Background / Text)", "Font Size (14pt / 18pt)", and "WCAG Filter" to establish the base global variables.
  2. 2. Calculate Color Codes (Execute Gradient Loop):
    Loops through each gradation from coordinate i = 255 to 0, independently generating the physical HEX value for each cell's color code (🔴R, 🟡R+G, 🟢G, 🟢🔵G+B, 🔵B, 🟣R+B, ⚪R+G+B).
  3. 3. Calculate Contrast Ratio Against Black (Physical Measurement):
    Mathematically calculates the contrast ratio of each cell against pure black (#000000) by finding the relative luminance (lum function) multiplying human luminous efficiency ratio and γ conversion to normalized linear RGB (lin function). This is a pure physical measurement value regardless of background/text role.
  4. ★ 3.5. Apply Halation / Intraocular Scattering Model (Effective Legibility Correction):
    Under the most optically disadvantageous condition of "Color Text on Black Background (Render Mode = text)" and "Thin Font (Font Size = 14pt)", it corrects contrast attenuation due to Intraocular Scattering / Straylight. It adjusts the scatter noise value from the physical contrast ratio to dynamically degrade (downward correct) the "effective contrast ratio" perceived on the retina, sending it to the next decision step.
  5. 4. Switch Contrast Ratio by Render Mode:
    In text coloring mode (text), it calculates the contrast ratio with the combination of "Color Text vs. Black Background (#000000)". In background fill mode (bg), since each color is applied to the background, it calculates ITU-R BT.601 Perceived Lightness (0.299R + 0.587G + 0.114B). If lightness exceeds the threshold (140), it performs Auto Inversion of the text color to black (#000000), or below it to white (#FFFFFF). The contrast ratio is recalculated with the actual combination of "auto-selected text color vs. background color".
  6. 5. Execute WCAG Conformance Judgment Based on Font Size:
    It individually maps each cell to a conformance level (AAA / AA / AA-L / NG) by checking the "effective contrast ratio" calculated in step 4/4.5 against the judgment criteria of the font size (14pt / 18pt) selected in step 1.
  7. 6. Determine Applied CSS (Color Scheme):
    Determines the color scheme style based on the render mode. If in background fill mode (bg), each color is applied to the cell's background, and the text color uses the auto-inverted white/black. If in text coloring mode (text), the background is black and the text itself is colored. It simultaneously applies font size to the cell CSS.
  8. 7. Execute Filter Conformance Judgment:
    Matches the state of the "WCAG Filter" selected in step 1 with the judgment level in step 5. It dynamically applies a .dimmed class that lowers opacity to 12% and turns monochrome to cells that do not conform.
  9. 8. DOM Insertion and Screen Render:
    Batches insert all cell configuration info (inline CSS, text, badges, dimming classes) into the HTML tree (DOM) and re-renders it on the screen.

Principles of Optimization

The 8‑bit per channel RGB space enumerates 16,777,216 discrete colors. From a systems perspective, however, this nominally large space conceals significant redundancy for UI themes: many distinct color tuples are functionally equivalent once rendered under limited opacity compositing and display quantization. We therefore adopt a principled constraint: select channel values that are binary‑aligned (powers‑of‑two fractions of 256). This constraint enables integer‑only arithmetic in common blending paths and reduces end‑to‑end rendering latency.

1. Bit‑shift algebra and hardware implications

Alpha compositing in typical 8‑bit pipelines computes, per channel, an expression equivalent to: $$dst = \frac{src \times k + dst \times (255-k)}{255},$$ where $k$ is the integer alpha in [0,255]. When $k$ is a multiple of 1 and the denominator is 255, implementations normally use floating‑point multiplication and a costly division (FDIV). By constraining $k$ to values expressible as $k = m\times(256/2^n)$ (for small integer $m,n$), the same computation can be rearranged into integer add/shift forms such as: $$dst = ((src\times k + dst\times(256-k)) + 128) >> 8,$$ which requires only integer multiply, add and a single right shift. On conventional CPUs and GPUs this replaces multi‑cycle FDIV instructions with single‑cycle shifts (SHR) and integer arithmetic, materially reducing per‑pixel latency at scale.

2. Canonical representation and operational efficiency

Enforcing a canonical, binary‑aligned palette has both runtime and operational benefits:

  • Deterministic integer math: Channel values such as 0xFF, 0xBF, 0x80, 0x40 correspond to 100%, 75%, 50% and 25% and permit integer shift semantics without remainder.
  • Reduced configuration surface: A small set of canonical colors reduces cognitive load, simplifies diffusion of theme settings, and minimizes storage/transfer redundancies in text formats.
  • Textual normalization: While the benefit is secondary to runtime arithmetic, representing colors in compact forms (e.g. 3‑digit hex where applicable) reduces configuration payload and encourages reuse of canonical values across JSON settings and style sheets.

3. Practical implementation boundaries

Editor configuration files (e.g. VS Code's JSON) are declarative and cannot perform bit operations; nevertheless selecting canonical values is a pragmatic design choice. It aligns authoring ergonomics (readability, typing speed) with measurable runtime advantages by ensuring the renderer receives values that map to fast integer paths.

Digital 8-bit color channels operate from 0 to 255 (256 levels). Dividing the spectrum using binary bit-shifting (>> 1) divides values exactly by 2 with no mathematical remainder, creating a clean, high-performance shading scale. This binary-aligned color scale is not merely a design preference; it is specifically structured to align with the core optimization principles of computer hardware.

Silicon Lottery, Replication Drift & Frequency Scaling

In semiconductor fabrication, microscopic variations in silicon density and path placement lead to the Silicon Lottery (performance and thermal output variability among identical chips, detailed in IEEE Spectrum: Did You Win the GPU Cloud Lottery?, and mathematically modeled for spatial variations in ACS Photonics: Capturing the Effects of Spatial Process Variations). These physical discrepancies prevent identical processors from running at the exact same clock speed under identical workloads, causing execution time and benchmark reproducibility to drift. When hardware dynamically scales clocks via DVFS (Dynamic Voltage and Frequency Scaling), internal Phase-Locked Loops (PLLs) adjust dividers via binary ratios. Storing colors natively on bit-shift boundaries reduces mathematical scaling logic, minimizing dynamic thermal overhead and helping individual cores maintain stable clock synchronicity.

Hardware Alignment (Dual Channel Memory & GPU)

Anyone who has purchased memory modules knows the experience of buying matching dual, triple, or quad kits to ensure perfect timing synchronicity and prevent memory channel mismatching. Just as PC builders select matching Dual-Channel RAM kits to avoid hardware bottlenecks (detailed in Intel Corporation: DDR Memory Architecture and Interleaving), compilers and GPUs rely on binary alignment to prevent performance lag. By using exact coefficients (FF, BF, 80, 40, 00), the GPU or CPU can compute alpha blending, scaling, and contrast checks using cheap bit-shifts instead of heavy fractional floating-point divisions.

Lockstep Synchronicity & Parallel Rendering

In safety-critical fault-tolerant computing, systems run in Lockstep—executing identical operations on multiple processing units in perfect clock-cycle sync. Modern GPU multi-threaded shader cores (SIMT) run colors under a similar paradigm (analyzed in IEEE Xplore: Quantifying Performance Variability in GPU Clusters). Storing and feeding binary-aligned, bit-shifted colors avoids execution divergence between threads (e.g., conditional rounding logic differences), ensuring that thousands of pixel-rendering pipelines remain locked in step for maximum performance.

Coherent Output: Respecting the Hardware Engine

Since custom PC builders carefully assemble, upgrade, and benchmark hardware (RAM, CPUs, GPUs) designed entirely around binary-aligned bit-shift efficiency, the final layer—the screen's visual output—should respect this same mathematical architecture. Aligning software color definitions with the physical architecture of the machine ensures a unified computational design: hardware optimized for binary precision running colors formulated on the exact same principles, avoiding fractional mathematical discrepancies at the final rendering stage.

Mathematical Drift & Unaligned Color Examples

Most standard design palettes (over 95% of standard web color codes) rely on color coordinates that do not align with binary division boundaries. When these values are blended, scaled, or adjusted (which internally divides values), any channel containing an odd number (where the lowest binary bit is 1) instantly spills a fractional remainder of 0.5 upon a single right shift. Because CPU/GPU integer registers cannot hold fractional remainders, this mathematical mismatch forces the processor to promote the values to floating-point representation, perform expensive decimal division, and call truncation/rounding operations (such as floor() or round()) across millions of pixels.

Benchmarking & V8 Optimization Hurdles

To mathematically prove the rendering latency differences, we engineered a dedicated test harness (color-benchmark.html). During this implementation, we uncovered and actively bypassed several key runtime optimization barriers built into browser engines (like Chrome's V8) that hide true hardware latency:

  • Dead Code Elimination (JIT Skip): Modern compilers automatically drop loops whose output variables are never used or displayed. To prevent this, our tests accumulate loop products into global variables and print final checksums to force full iteration evaluation.
  • Object Property Lookup Bottleneck: Accessing object variables (like color.r) forces dynamic lookup hash-table checks in unoptimized interpreter states, adding a massive lookup delay that completely eclipses the instruction execution difference. Bypassing this bottleneck requires flattening objects into direct CPU-register-friendly local scalar variables.
  • JIT Warm-up & Cache Contamination: Measuring both tests sequentially in the same execution context creates unfair bias due to JIT compilation engine warm-up overhead and L1/L2 cache contamination. For maximum measurement parity, we separated the tests into standalone pages (conventional.html and optimized.html) to run each rendering test in a clean, isolated thread context.

function runOptimizedTest() {
  const start = performance.now();
  for (let y = 0; y < height; y++) {
    const weight = Math.round((y / height) * 255);
    const invWeight = 255 - weight;
    for (let x = 0; x < width; x++) {
      const prodR = c1.r * weight + c2.r * invWeight + 128;

      data[idx + 2] = (prodB + (prodB >> 8)) >> 8; // B (No division)

      data[idx + 3] = 255;
      idx += 4;
    }
  }
  ctx.putImageData(imgData, 0, 0);
  const end = performance.now();
  document.getElementById("timeResult").innerText = (end - start).toFixed(2) + " ms";
}

Visual Effects, OS Performance Controls & Hardware Latency

The correlation between rendering calculations and machine latency is a fundamental engineering reality. Every major operating system implements visual bypass settings specifically designed to avoid pixel-blending bottlenecks under limited hardware or power constraints:

  • Windows Performance Options: Setting Windows to "Adjust for best performance" strips away window drop shadows and font anti-aliasing. This action physically reduces the unique active color count on screen from thousands of blended values down to a dozen base integer colors, completely bypassing intermediate float division cycles.
  • Apple iOS & macOS (Reduce Transparency): Turning on "Reduce Transparency" replaces blurred, semi-transparent overlays with solid flat backdrops. Apple's developer guidelines (Performance and Optimization) note that reducing alpha channels limits the mathematical operations per fragment, directly preserving GPU clock cycles and battery life.
  • Google Android (Debug GPU Overdraw): Android developer utilities feature a visual overdraw debugging mode to identify pixels colored multiple times per frame. Because each overlap demands an alpha-blending multiplication, minimizing overdraw is critical to maintaining high frame rates and staying within device thermal limits.
  • Linux (Bypass Compositor): X11 and Wayland window managers (such as GNOME's Mutter or KDE's KWin) automatically bypass the desktop compositor in full-screen mode (unredirection). Bypassing composite rendering cuts out secondary alpha-blending and matrix scaling, reducing latency from multiple frames to sub-millisecond ranges to prevent GPU pipeline stalls.

While these OS settings achieve optimization by degrading the visual interface (forcing flat, aliased layouts), our Mathematical Color Scale achieves the same computation relief at the source level. By ensuring base colors are binary-aligned, we preserve beautiful neon styles while enabling the graphics pipeline to execute color blending at native hardware speed.

Absolute 0-255 Byte Coordinates vs. Abstract Intensity Scales

In web development, abstract scales (such as 100-900 intensity classes popularized by CSS utility frameworks) offer an approachable, high-level way to manage visual hierarchies. However, these systems decouple design values from the underlying RGB/RGBA physical byte domain. In contrast, our methodology adopts the absolute 0-255 byte model, which is the native language of graphic hardware and display controllers. Under this coordinate-based approach, the scale maps directly to byte boundaries (0 for zero-emission/black, 255 for full-intensity/white). For design efficiency, we group coordinates into clean step intervals (such as 5, 10, 20...), allowing developers to easily grasp relative brightness while preserving the mathematical flexibility to perform precise micro-tuning (e.g., adjusting 250 to 255, or inserting a mid-step 15) within the same absolute space. This clean listing paradigm matches structural rendering optimizations historically deployed in layout frameworks (e.g., Joao Moreno's 2017 optimizations in the VS Code Tree & Explorer Performance via Flat Virtualized Lists).
